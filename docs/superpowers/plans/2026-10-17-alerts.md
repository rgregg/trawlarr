# Alerts Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Push a JSON webhook to user-defined destinations when a file, node, library or scan needs a person, and let a flow send its own message, without a dead receiver ever affecting a job.

**Architecture:** A pure coalescer in `@trawlarr/core` decides what is sent now, held, or summarised. The server owns destinations (a new `alerts` settings section, secrets masked at the API), a bounded asynchronous deliverer, and an `AlertService` that both the daemon event bus and a flow node feed. A flow node never sees a destination URL: it sends an `alert-request` agent message and the daemon delivers, locally or from a remote node.

**Tech Stack:** TypeScript (strict, project references), better-sqlite3 `setting` table, Node `http` for test receivers, React + Vite for the settings UI, vitest.

**Spec:** `docs/superpowers/specs/2026-10-17-alerts-design.md` (§11 holds the review calls; treat them as part of the spec).

## Global Constraints

- `@trawlarr/core` does no I/O and reads no clock; time enters as a `nowMs` parameter (ESLint enforces it).
- Dependencies flow one way: `plugin-api` → `core` → `plugins-core` → `engine` → `server`. The Send Webhook node must not import `server`.
- Feature name in code and UI is **Alerts**, never "notifications" (that word means the inbound `/notify/arr` hooks).
- Destination URLs, header values, the API key and Plex tokens never appear in an API response after save, a log line, a payload, or the flow definition. A failure log names the destination, not its URL.
- Only `http:` and `https:` URLs are accepted.
- Defaults: coalescing window **15 min**; **10 distinct causes per library per window**; "still down" repeat at most **hourly**; delivery timeout **10 s**, **3 retries**; failure and `.recovered` rules exactly as spec §3.
- A new destination has **all** event toggles on. A single retried failed attempt never alerts.
- Payload field names are a wire contract: additive changes only. `PROTOCOL_VERSION` is **not** bumped (the new agent message is additive; an older daemon drops it, which spec §11.6 accepts).
- Daemon alerts subscribe to the bus; a listener must never throw into the emitting path, and sending never blocks a job, scan, claim or shutdown.
- Migrations are forward-only, numbered; this plan needs **none** (storage is a `setting` section).
- UI copy is terse: short labels, no help paragraphs.
- Comments explain why, citing the defect the rule prevents.
- Test scope: run only the touched package or file (`pnpm test -- <path>`); never the full suite locally. Run `pnpm typecheck` and `pnpm lint` before the final commit of each task.

## Review Focus

- A receiver that accepts the connection and never answers: shutdown must still finish by the drain deadline and report the dropped count (Task 3, Task 4).
- A destination URL carrying credentials in its query string (`?token=…`): it must not appear in the failure log line, the API response, or any payload (Task 2, Task 3, Task 5).
- Thousands of `file.failed` events with distinct paths but one cause, plus a second unrelated cause in the same window: first message at once, one summary, and the second cause not hidden (Task 1).
- A Send Webhook node placed after Hold for Review never runs, because Hold throws and has no outputs: the node's tooltip must say to place it before the hold (Task 8).
- A node newer than its daemon sends `alert-request`; the daemon drops it silently and the flow must still finish (Task 6).
- A public base URL with a trailing slash or a path prefix (`https://host/trawlarr/`) must still yield a correct job link (Task 4).

  - `type AlertEventType`, `type RecoverableEventType = Exclude<AlertEventType, 'file.failed' | 'file.not_converging'>`

  - `createCoalescer(opts: { windowMs: number; maxCausesPerWindow: number; repeatMs: number }): Coalescer`
  - `interface Coalescer { offer(i: { event: AlertEventName; scope: string; cause: string; example?: string; nowMs: number }): { send: boolean }; due(nowMs: number): FollowUp[]; clear(event: AlertEventName, scope: string): void }`
  - `interface FollowUp { event: AlertEventName; scope: string; kind: 'summary' | 'still-down'; count: number; otherCauses: number; examples: string[] }`

- [ ] **Step 1: Write failing tests** in `alerts.test.ts`:
  - `normalizeCause` maps `"ffmpeg exited 1 at /library/a/b.mkv (attempt 3)"` and `"ffmpeg exited 1 at /library/c/d.mkv (attempt 2)"` to the same string; two reasons differing in words map to different strings.
  - First `offer` for a key returns `{ send: true }`; 2,000 further offers with the same key inside `windowMs` return `{ send: false }`, and `due(windowMs + 1)` returns exactly one `summary` with `count: 2000` and at most 3 `examples`.
  - 12 distinct causes in one window for one library: the first 10 send, and the follow-up carries `otherCauses: 2`.
  - `still-down` kind: an outage event offered again every minute for 3 hours yields `due` follow-ups no more often than `repeatMs` (assert ≤ 3 in 3 h at `repeatMs` = 1 h).
  - `clear(event, scope)` resets the key so the next offer sends at once.

- [ ] **Step 3:** Implement in `alerts.ts`. `normalizeCause` strips paths, digits and quoted names, collapses whitespace, lowercases. The coalescer is a `Map` keyed `event|scope|cause`, with per-window cause counts keyed `event|scope`. Comment why the cause cap exists: a loose key floods, a tight key hides a second failure.
- [ ] **Step 4:** Run the test again. Expected: PASS.
- [ ] **Step 5:** `pnpm typecheck && pnpm lint`, then commit: `feat(core): coalesce alerts by cause so one outage is one message, not thousands`.
