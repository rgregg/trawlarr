# P2b — The Daemon Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn trawlarr from a set of one-shot commands into a long-lived service that watches libraries, schedules concurrent isolated workers, and exposes the whole system over an HTTP + WebSocket API.

**Architecture:** One daemon process owns the SQLite connection, the scanner, the watcher, the schedule and the worker supervisor. Work runs in forked child processes that never touch the database and speak a JSON job protocol over their IPC channel — the same protocol that becomes the remote-node transport in v1.2. A REST API over `node:http` serves everything durable; one WebSocket carries what changes second to second. The CLI keeps working, but when a daemon owns a data directory the CLI becomes a client of its API rather than a second writer.

**Tech Stack:** Node 22, TypeScript, better-sqlite3, `node:http`, `ws` (MIT), `chokidar` (MIT), vitest, ffmpeg/ffprobe 6.1.1.

## Why this scope

P2a converges a library end to end and then goes quiet: a human runs `scan`, then `run`, and nothing happens again until they do. This plan delivers everything needed to stop being a human cron job — and nothing else.

**In:** a daemon that owns the scan/drain cycle; the HTTP API of spec §3.5 with a WebSocket push channel; a filesystem watcher and a periodic rescan; worker classes, hardware caps and real concurrency with workers as isolated child processes; schedule windows; and `library.paused_reason` finally populated by flow validation.

**Out, explicitly, for the phase after this one:** the web UI (spec §8); the Docker image with all six binaries; plugin source syncing and the plugin browser backend (`plugin_source` CRUD, `POST /plugins/sources/:id/sync`, the browse endpoints); per-job log files on disk (`job.log_path` stays NULL — step excerpts in `job_step` and the live WebSocket tail are what exist); and the synthetic 100k-file scan benchmark. Also out: the flow **template gallery** (spec §6.3) — the templates are UI data and ship with the UI; `POST /flows` accepts a definition and that is enough for a scriptable client.

## Guidance: follow Tdarr's shapes

Plugin compatibility is the highest priority, and users arriving from Tdarr should find familiar concepts. Match Tdarr's *behaviour* for worker classes, schedules and library options rather than inventing new vocabulary. Deviate only where trawlarr has already decided differently on purpose: flow-only plugins, the signature/convergence model, the explicit Replace Original File node, and MIT licensing. **Never copy Tdarr code, comments or type definitions.**

Two places this bites in this plan, both resolved below rather than left to judgement:

- **Worker vocabulary.** Tdarr has a flat worker-type namespace (`transcodecpu`, `transcodegpu`, and the health-check equivalents). Spec §4.4 deliberately splits that into a **class** (`transcode` / `health`) and a separate **hardware type**, because hardware carries its own concurrency cap independent of pool size. Trawlarr keeps the split internally, and **projects the flat Tdarr string at the plugin boundary** so `args.workerType` reads exactly what a community plugin expects (Task 3).
- **Schedules.** Tdarr expresses a schedule as a weekly grid of hours per worker type, and pausing is a period with no workers. Trawlarr matches that shape exactly (Task 2): windows carry counts, and a window with zero is a pause. Trawlarr adds only what spec §4.5 already decided — an explicitly configured timezone rather than the host's.

## The four design problems, resolved

Read this section before Task 1. Each of these is a place the implementation goes wrong if it is decided by accident.

### 1. Concurrency: what the single-worker assumption actually was

`claimNext` is atomic, so two workers can never take the same file. Nothing else in P2a was written for parallel workers, and one race was already found and fixed: **a file mid-replacement belongs to no row.** `Replace Original File` renames the new file into place, `runJob` probes it, and only then does `updateAfterRun` record the new identity. In that window the file on disk has an identity no row claims. A scan walking it matched nothing, inserted a *second* row, and `updateAfterRun` then hit `UNIQUE (library_id, content_key)` and unwound the run — leaving a ghost row holding the *pre-transcode* probe that got claimed again after its backoff and re-transcoded an already-transcoded file, with generational loss, pushing the good result into trash. Two `good` rows for one file, "100% converged", one of them a phantom.

The fix lives in `scanner/scan-library.ts`: a walked file that **no row claims**, at a path an **in-flight run is entitled to produce** (same directory and stem as a `running` row's path — Replace keeps the user's stem and may only change the container), is left entirely alone.

**That fix's assumption was never "one worker".** It was two things, and both survive this plan by construction:

- `claimNext` commits `running` **strictly before** the run can put anything on disk. Preserved: Task 4 claims in the daemon and only then builds a payload and dispatches it to a worker, so the commit strictly precedes the fork.
- `listRunningPaths` is queried **fresh per walked file**, never cached for the length of a scan. Preserved and now load-bearing for a second reason: with N workers there are up to N running rows at once, and a job that starts mid-scan must still be covered. Task 8's scan coordinator must not "optimise" this into a per-scan snapshot.

What is **genuinely new** under N workers is two workers choosing the same destination path simultaneously. Two shapes are real: two files sharing a basename (`title00.mkv` under two show folders is ordinary for disc rips) colliding in a per-root trash directory, and two files converging on one replacement path (`movie.mkv` and `movie.avi` both targeting `movie.mp4`). Check-then-act loses both: both workers `lstat`, both see `ENOENT`, and the second `rename` silently destroys the first's work. This is already closed — `packages/engine/src/executor/replace-original.ts` reserves the destination with `open(path, 'wx')` (`O_CREAT|O_EXCL`) and renames over its own placeholder. `link(2)` is *not* an acceptable substitute: it fails `EPERM` under the kernel default `fs.protected_hardlinks=1` whenever the caller neither owns the source nor has read+write on it (a container running as PUID 1000 over media owned by another uid at 0644, on plain ext4 — an ordinary deployment), and every fallback for that degrades to check-then-rename and reopens the race permanently while the code reads as safe. Task 7 adds the two-worker regression test that pins it.

Finally: the daemon is a **single process with a single synchronous better-sqlite3 connection**, so no two database operations interleave. Worker concurrency is process concurrency for *transcoding*, not for database access.

### 2. Database ownership

Spec §3.3: **the server is the only process that ever opens the database.** Today the CLI opens it directly, and `scan` and `run` are separate processes against one WAL file. A daemon holding it open while a CLI writes is how you get `SQLITE_BUSY` in the middle of a claim, and it is the shape that produced the ghost-row bug above.

**The model:** a daemon that owns a data directory advertises itself in `<data-dir>/daemon.json`, created with `open(path, 'wx')` and removed on exit, containing `{pid, bind, port, apiKey, startedAt, schemaVersion}`. Every CLI invocation resolves that file first:

- **No file, or a file whose `pid` is dead** (`process.kill(pid, 0)` throws `ESRCH`) — the CLI opens the database directly and behaves exactly as it does today. A stale file is taken over, not obeyed.
- **A file whose `pid` is alive** — the CLI is a *client*. Every command routes through the HTTP API with the file's `apiKey`. The CLI never opens the database at all.

Workers never open it either — that is what Task 4's payload/report split buys, and it is what makes the same protocol work over a WebSocket for remote nodes in v1.2 without a second code path.

### 3. Cancellation reaches the process group

`packages/engine/src/ffmpeg/process-group.ts` exists because `runFfmpeg` spawns ffmpeg with `detached: true`, making it a process-group **leader** so one `kill(-pid)` reaches a plugin-spawned descendant too. Workers becoming separate processes is exactly what it was built for, and the cancellation path is layered:

1. Daemon sends `{type: 'cancel'}` down the worker's IPC channel.
2. The worker aborts its in-flight `runFfmpeg` via the `AbortSignal` it already accepts, which kills ffmpeg's whole group, then reports `{type: 'done', outcome: 'cancelled'}` and exits 0.
3. If the worker has not exited within a grace period, the daemon kills the **worker's own process group** — the worker is forked `detached: true` for precisely this reason — with SIGTERM then SIGKILL.

Two guards in `killProcessGroup` are load-bearing and must not be worked around: pgid `0` means "my own group" and would kill the daemon and every sibling worker; pgid `1` means "everything I may signal". Both are refused rather than translated. And `killFn` is injectable purely so a test driving a **fake** child cannot signal a real group — a fake pid plus a real `process.kill(-pid)` is a live grenade in a test suite. Every test in this plan that exercises a kill path injects `killFn`.

### 4. A schedule window closing mid-transcode: finish, never cancel

**Decision: the current job runs to completion. Workers retire on completion, never mid-file.**

A schedule window sets the *target* pool size per class. When the target falls, the supervisor stops starting new work and lets running workers finish; the pool reaches its new size as jobs complete. A window with zero workers is a pause, exactly as in Tdarr.

Justification: cancelling a transcode two hours in produces nothing and costs everything. The file backs off and is re-transcoded from scratch later, so the machine does *more* total work — in exactly the hours the user configured the window to protect. The asymmetry is stark: finishing costs at most one job's remaining runtime past the boundary, once; cancelling costs a whole job's elapsed runtime, and pays it again later. A user who genuinely wants a hard stop has one: `POST /api/v1/jobs/:id/cancel`, which is explicit, per-job, and leaves an audit trail. Silent destruction of hours of work is not a thing a schedule should do.

The consequence is stated in the API and the README rather than discovered: "a window closing does not interrupt work already in progress."

- [ ] **Step 3: Implement**

Store each group as one JSON value under a dotted key (`daemon`, `binaries`, `scan`, `hardware`, `schedule`), merged over the defaults on read. Validation runs on **both** read and write: on write so a bad value cannot be stored, on read so a hand-edited row is a named error rather than a downstream mystery.

```ts
const SETTING_KEYS = {
  daemon: 'daemon',
  binaries: 'binaries',
  scan: 'scan',
  hardware: 'hardware',
  schedule: 'schedule',
} as const;

const requireWholeNumber = (value: unknown, label: string, min: number, max: number): number => {
  if (typeof value !== 'number' || !Number.isInteger(value) || value < min || value > max) {
    throw new SettingValidationError(
      `${label} must be a whole number between ${min} and ${max}, got ${JSON.stringify(value)}.`,
    );
  }
  return value;
};
```

The API key is generated lazily inside a single write transaction on first read, so two concurrent readers cannot mint two keys. Do not memoise settings in the repo instance: the daemon and the API both read through the same repo and a `PUT /api/v1/schedule` must take effect on the supervisor's next tick.

This matches Tdarr's shape — a weekly grid of periods carrying worker counts, with a pause expressed as a period of zero — and adds only what spec §4.5 already decided: an explicitly configured timezone, so a container with `TZ` unset does not silently shift everyone's overnight window.

**Later windows win.** When two windows are active at once, the last one in the array that names a class sets that class's count. This is the only rule that is simple enough to explain in a UI, and it makes "six overnight, except zero on Sunday morning" expressible by ordering rather than by precedence arithmetic.

**On DST.** Spec §4.5 says ambiguous and skipped local times resolve to the earlier real instant. This implementation never converts a local wall-clock boundary into an instant — it converts the *current instant* into local wall-clock and asks whether that is inside a window, which is always well-defined in that direction. The supervisor re-evaluates on every tick rather than firing at boundaries, so "which instant does 01:30 mean" is unobservable: on a spring-forward day a 01:00–02:00 window simply never becomes active, and on a fall-back day it is active across both passes. Record this in the function's doc comment; it is a behavioural detail someone will otherwise rediscover from a support ticket.

`zonedInstant` uses `Intl.DateTimeFormat` with `timeZone` and `hourCycle: 'h23'` — Node 22 ships full ICU, so no dependency is required. **`core` never reads the clock:** `nowMs` is a parameter, always.

```ts
const WEEKDAY_INDEX: Record<string, number> = {
  Sun: 0, Mon: 1, Tue: 2, Wed: 3, Thu: 4, Fri: 5, Sat: 6,
};

export const zonedInstant = (input: { nowMs: number; timezone: string }): ZonedInstant => {
  const parts = new Intl.DateTimeFormat('en-US', {
    timeZone: input.timezone,
    weekday: 'short',
    hour: '2-digit',
    minute: '2-digit',
    hourCycle: 'h23',
  }).formatToParts(new Date(input.nowMs));
  const find = (type: string) => parts.find((part) => part.type === type)?.value ?? '';
  return {
    weekday: WEEKDAY_INDEX[find('weekday')] ?? 0,
    minuteOfDay: Number(find('hour')) * 60 + Number(find('minute')),
  };
};
```

`windowContains` is where the wrap rule lives, and the day check must be applied to the day the window *started*:

```ts
export const windowContains = (window: ScheduleWindow, at: ZonedInstant): boolean => {
  const wraps = window.endMinute <= window.startMinute;
  const inSpan = wraps
    ? at.minuteOfDay >= window.startMinute || at.minuteOfDay < window.endMinute
    : at.minuteOfDay >= window.startMinute && at.minuteOfDay < window.endMinute;
  if (!inSpan) return false;
  if (window.days.length === 0) return true;
  // A wrapping window that we are in BEFORE its end minute began yesterday.
  const startedOn =
    wraps && at.minuteOfDay < window.endMinute ? (at.weekday + 6) % 7 : at.weekday;
  return window.days.includes(startedOn);
};
```

The escalation, in order, with nothing skipped:

1. `cancel()` sends `{type: 'cancel'}`. The agent aborts its `AbortController`, which `runFfmpeg` already turns into SIGKILL to **ffmpeg's** process group — reaching a plugin-spawned descendant, which is the whole reason `detached: true` is there.
2. The agent reports `{type: 'done', report: {…, cancelled: true}}` and exits 0.
3. If it has not exited within `cancelGraceMs` (default 30s, injected timer), the daemon kills the **worker's own** group: SIGTERM, then SIGKILL after a second grace period.

**A cancelled job is requeued, not penalised.** `applyJobCancelled` calls `mediaFileRepo.requeue`, which clears the attempt count and backoff. A human pressing cancel is not evidence the file is bad, and burning an attempt on it would push a healthy file toward `failed` after three interruptions.

**Two guards must not be worked around.** `killProcessGroup` refuses pgid `0` (my own group — would kill the daemon and every sibling worker) and pgid `1` (everything I may signal). Neither can be a child we spawned. And **every test here injects `killFn`**: a fake child's pid belongs to some unrelated real process or to nothing at all, and a fake pid plus a real `process.kill(-pid)` is a live grenade in a test suite. The fake child's pid is `undefined` by default for the same reason.

The supervisor replaces `runQueue` as the daemon's drain mechanism. **`runQueue` stays exactly as it is** — `trawlarr run` without a daemon still uses it, and its `repeatClaimStop` diagnostic is not being re-derived. Do not delete it, do not "unify" them.

What `tick()` does, in order:

1. `target = evaluateSchedule({schedule: settings.getSchedule(), nowMs: nowMs()})`.
2. If paused, or the target for a class is below the number of running workers of that class, **start nothing** for that class. Never kill: see Design Problem 4. The pool shrinks as jobs complete.
3. For each class under target, and while the **hardware caps** allow, claim a file and start a worker.

**The hardware cap is checked before the claim, not after.** `settings.getHardware().caps` gives, say, `{nvenc: 2}`. A claim that would start a third NVENC job is not made at all — claiming and then unwinding would leave a row `running` that nothing is going to finish. Concretely: compute the set of libraries whose flow's `flowRequiredHardware` is satisfiable *right now* by this node's remaining hardware headroom, and pass exactly that set as `claimNext`'s `libraryIds`. A library requiring `nvenc` on a node whose `available` list has no `nvenc` is never in that set, so spec §4.4's "a node that detects no GPU will not be handed GPU-requiring work" is true by construction rather than by a check somewhere downstream.

**Library pause is honoured the same way `runQueue` does it** — the enabled set is recomputed before every claim, intersected with the hardware-eligible set, and passed explicitly. `claimNext` has no notion of "enabled"; a paused library's files are never claimed rather than claimed-then-abandoned.

Spec §4.1: three triggers, **one code path**. The coordinator's whole job is to be that one code path — everything funnels into `request()`, which calls the existing `scanLibrary` and nothing else. Do not add a second, cheaper "just this one file" scan path; a per-file fast path is a second implementation of identity resolution and signature recomputation, and the second copy is the one that will be wrong.

Four rules, each of which is a bug if omitted:

- **One scan per library at a time.** A watch event arriving during a scan sets a dirty flag; the coordinator re-scans once when the current scan ends. Without this a directory copy produces one concurrent scan per file.
- **Debounce and settle.** A watch event schedules a scan `settleMs` (default 30s) later, and each further event for the same library resets the timer. A file still being copied has a growing size and an unfinished container; probing it mid-write admits garbage. Tdarr holds new files for the same reason.
- **The watcher ignores exactly what the walk prunes.** `reservedDirsForLibrary(library)` — the same helper, not a re-derived list. Staging and trash default to `<root>/.trawlarr/...`, *inside* the root, deliberately, so a move is a same-device atomic rename. The scanner had no hidden-directory skip once and ingested both as library media: a half-written staged transcode probed mid-write, a trashed file re-added and re-queued so trash became a loop that resurrects what the user deleted, and — worst — identity being `(device, inode)` meant trashing an original made the *existing* record match the trashed copy and rewrite its path into the trash, while the replacement at the original path was admitted as a second record. **Every duplicate of a path-containment check is a latent version of the same bug; the weaker copy is the one that will be called.**
- **The periodic rescan is not optional.** Network mounts drop events, and chokidar over NFS/SMB is unreliable in exactly the deployments this tool targets. Default one hour, from `settings.getScan().rescanIntervalMs`, with the timer injected.

`chokidar` (MIT) is what spec §4.1 names. Add it to `packages/server` only, commit the lockfile in the same commit, and run `pnpm audit:licenses`.

Spec §6.5: an invalid flow **pauses its libraries with a stated reason** rather than failing every file individually. Ten thousand identical failures in the job list is not a diagnosis; one paused library naming the missing plugin is. The column and the supervisor's honouring of it already exist; nothing has ever written it.

What counts as invalid, in priority order, with the reason naming the fix:

1. The library has no flow attached → `flow-invalid: no flow attached. Run "trawlarr library set-flow".`
2. `flowId` references a flow that no longer exists.
3. `validateFlowDefinition` rejects the stored definition. **A stored flow can become invalid without anyone editing it**, because a plugin update changes what `details()` declares — which is exactly why this runs at daemon start and on every flow or library change, not only on save.
4. A node names a plugin this host cannot resolve → name the plugin id. Note `validateFlowDefinition` treats an unresolvable plugin as *unknown, not wrong*, and one unresolvable node suppresses its no-start-node verdict entirely (it may be the start). So an unresolvable plugin must be reported here as its own reason rather than being inferred from a validation silence.

**Ownership of the pause matters.** An operator who paused a library through the API must not be un-paused by a flow becoming valid, and a flow-validation pause must not be cleared by hand only to reappear. The reason string's prefix records the owner: `checkLibraryHealth` sets and clears only reasons beginning with `PAUSE_PREFIX_FLOW`, and leaves an `operator:` pause strictly alone. The API's pause endpoint writes `operator: ` + whatever the caller said. No schema change: the prefix is the marker.

A named 501 is a five-minute fix for a client author; a bare 404 is a bug hunt.

Notes that are decisions, not details:

- `GET /system/version` returns `{version, schemaVersion, contractLevel, binaries}`. `contractLevel` is reported as `null` with a `note` field saying version reporting is unimplemented (spec §2.10) — claiming a contract level trawlarr does not implement, to make a warning go away, is explicitly rejected by the spec. `binaries` reports, for each of ffmpeg/ffprobe, the configured path and whether spawning it with `-version` succeeds. That is *checking configured paths*, not hardware detection; say so in the field name (`resolved: boolean`) so nobody reads it as a capability probe.
- `GET /nodes` reads the `node` table and joins the supervisor's live status onto it. The `node` table exists and nothing has ever written it, so this task adds `ensureLocalNode({db, settings})` in `packages/server/src/api/routes/nodes.ts`: upsert one row with `id: 'local'`, `access_mode: 'direct'`, the settings' hardware types, and `last_seen_at = nowMs()`. Call it when the API context is built. This also makes `job.node_id` (Task 4) meaningful — a job row that names no node is a job whose origin cannot be reconstructed, which is exactly what v1.2's multi-node support needs. v1 has one node; the endpoint is a list because remote nodes arrive here and a client written against an object would have to be rewritten.
- `POST /libraries/:id/scan` calls `scans.request(id, 'manual')` and returns `202` immediately. A scan takes minutes; a synchronous scan endpoint holds an HTTP connection open long enough for every proxy in the path to time out, and `better-sqlite3` being synchronous means the scan's chunked writes already interleave with the event loop rather than with this request.
- `PUT /workers/counts` writes `schedule.baseCounts` and calls `supervisor.tick()`. There is no separate "current counts" concept: the schedule is the single source of truth, and a base-count change taking effect immediately is what the UI's worker strip expects.
- `POST /libraries/:id/pause` writes `operator: <reason>` (Task 9). `POST /libraries/:id/resume` refuses, with `409`, to resume a library whose pause reason begins `flow-invalid: ` — and says which plugin is missing. Letting a user resume into an unrunnable state produces exactly the ten-thousand-identical-failures outcome §6.5 exists to prevent.
- `POST /flows/:id/dry-run` takes `{fileId}` and returns `runDryFlow`'s result including `classifySideEffects`' verdict. Spec §6.4 is explicit that a dry run **stops at the first node whose side effects it cannot vouch for**; the response names that node and why, and the API must not present a partial walk as complete.
- Authentication: `X-Api-Key` header compared against `settings.getDaemon().apiKey` with `crypto.timingSafeEqual` over equal-length buffers. `GET /system/health` is the only unauthenticated route, so a container health check needs no secret.

## Task 11: The WebSocket push channel

**Files:**
- Create: `packages/server/src/api/ws.ts`, `packages/server/src/api/ws.test.ts`
- Modify: `packages/server/src/api/server.ts`, `packages/server/package.json` (add `ws`, `@types/ws`), `pnpm-lock.yaml`

**Interfaces:**
- Consumes: `EventBus`, `SettingsRepo`, the `node:http` `Server` from Task 10.
- Produces:
  ```ts
  export interface WsChannel { close: () => Promise<void>; clientCount: () => number }
  export const attachWebSocket = (input: {
    server: Server; bus: EventBus; settings: SettingsRepo;
    path?: string;                                   // default '/api/v1/events'
  }) => WsChannel;
  ```

Spec §3.5: the socket carries worker progress, job state transitions, log tails and scan progress. **It is strictly a push channel for things that change second to second; everything durable is fetched over REST, so a dropped socket degrades liveness and never correctness.** That sentence is a design constraint, not commentary: nothing may be delivered *only* over the socket. Every event this channel emits corresponds to state a client can re-fetch from the API, which is what makes a reconnect a refresh rather than a resync protocol.

Rules:

- One `ws` server mounted on the same `node:http` server as the REST API, on `/api/v1/events`. One port, so one thing to expose and one thing to reverse-proxy.
- Authenticated on upgrade: `?apiKey=` query parameter or the `X-Api-Key` header. Browsers cannot set headers on a `WebSocket` constructor, so the query parameter has to exist — but reject the upgrade with `401` before the handshake completes rather than accepting and closing after.
- **Bounded outbound buffering.** A client that stops reading must not grow the daemon's memory without limit: if `socket.bufferedAmount` exceeds a cap (1 MB), drop `job.log` and `job.progress` for that client — the two high-rate, purely-cosmetic event types — and keep the state transitions. A slow browser tab is not a reason for the daemon to be OOM-killed.
- Every subscription is unsubscribed on close. A leaked bus listener per reconnect is a slow leak that only shows up after a week of uptime.

Add `ws` (MIT) and `@types/ws` to `packages/server`. Commit the lockfile in the same commit; run `pnpm audit:licenses`.

  ```ts
    pid: number; bind: string; port: number; apiKey: string;

  }
  export const createCliClient = (record: DaemonRecord) => CliClient;
  export class ApiRequestError extends Error { readonly status: number }
  ```

`startDaemon` is the composition root and does exactly this, in order:

1. Open and migrate the database. **Refuse to start on an unknown-future schema version** (spec §3.3) — a downgraded binary must not corrupt a newer database. `migrate` already handles this; make sure the daemon surfaces it as a named startup error rather than a stack trace.
2. Build the settings repo, event bus, supervisor, scan coordinator; `ensureLocalNode` (Task 10) so `job.node_id` has something to point at.
3. `checkAllLibraries` (Task 9), so an invalid flow pauses its library before any work is attempted.
4. Start the API server and attach the WebSocket. **Acquire the lock file only after the port is actually listening**, so its recorded port is real.
5. Request a startup scan for every enabled library; start the watcher and the rescan interval.
6. Start the supervisor tick interval, the trash-purge interval (daily, using each library's own flow-declared `trashRetentionDays`, exactly as `trawlarr run` does today), and the stall-reaper interval (hourly, `reapStalled`).
7. Install `SIGINT`/`SIGTERM` handlers that call `stop()`.

`stop()` shuts down in the reverse order and is the part most likely to be written carelessly: stop starting work → stop the watcher and timers → `supervisor.drain()` with a deadline (default 5 minutes, injected) → on deadline, `supervisor.stop()` which cancels through the process-group path → close the WebSocket and HTTP server → release the lock file → close the database. **A worker left running after the daemon exits is an orphaned ffmpeg writing into a library nothing is watching**, so the drain deadline is a real limit and not an unbounded wait.

**CLI routing.** Add a `resolveDaemon` step at the top of `dispatch` in `cli.ts`. When `readDaemonRecord` returns a record, every command becomes an API call through `createCliClient`; when it returns `null`, the CLI opens the database exactly as it does today. The user-visible output must be identical either way — a `status` that prints differently depending on whether a daemon happens to be running is a bug report waiting to be filed. New command:

```
trawlarr daemon [--data-dir <path>] [--port <n>] [--bind <addr>]
```

which starts the daemon in the foreground and logs its port and, on first run, its generated API key (once — it is in the database afterwards).

## Definition of done

- `pnpm build && pnpm lint && pnpm test` green from a **clean checkout** (no `dist/`), twice. `pnpm check:refs` and `pnpm audit:licenses` green. CI green.
- `trawlarr daemon` against a folder of h264 files converges the library with no further human action, at the configured concurrency, and goes quiet.
- A file dropped into a watched root is picked up and converged without a manual scan.
- Editing a flow through the API re-queues exactly the affected files, and they converge again.
- A schedule window with zero workers stops new work starting and does **not** interrupt work in progress.
- `POST /jobs/:id/cancel` kills ffmpeg and its descendants, and the file returns to `queued` with its attempt count cleared.
- A library whose flow references a missing plugin is paused with a reason naming that plugin, and cannot be resumed until the flow is fixed.
- Two workers running concurrently produce exactly one `media_file` row and one job per file, including while a scan runs.
- Stopping the daemon leaves no orphaned worker or ffmpeg process, and no `daemon.json`.
- The CLI produces identical output whether or not a daemon is running.
- No test asserts elapsed time. Every timer in production code is injectable.

## Not in this phase

The web UI (spec §8); the Docker image with all six binaries; plugin source syncing, the plugin browser backend, and `plugin_source` CRUD; per-job log files on disk (`job.log_path` stays NULL — `job_step` excerpts and the live WebSocket tail are what exist); the synthetic 100k-file scan benchmark; the flow template gallery (spec §6.3); contract-level version reporting (spec §2.10); and remote nodes (spec §4.8's Direct access and File transfer modes — the job protocol is shaped for them, and only the IPC transport is implemented).

Three things this plan declares without enforcing, so nobody mistakes them for working:

- **`@trawlarr/node-agent` is not a separate package.** The worker is a separate OS *process* running an entry point inside `packages/server`. The spec's process boundary and JSON protocol are both delivered; the package extraction is a v1.2 move, not a redesign.
- **`GET /jobs/:id/log` returns 501.** There is no full log on disk to serve until per-job log files land.
- **Hardware detection is configuration, not detection.** `settings.getHardware().available` is what the operator declares this node has. Nothing probes for an NVENC session limit or an available GPU yet; declaring `nvenc` on a machine without one produces failing jobs, exactly as it would in Tdarr.
